# 0005. Run history storage and database access (Phase 6)

- **Status:** Proposed
- **Date:** 2026-11-26

## Context
Phase 6 adds `POST /runs`, a live SSE stream (`GET /runs/{id}/events`) and Postgres for run history. The event log is the record of a run. It feeds the timeline, cost totals, the hash-chained audit trail (C11) and provenance, so it must be append-only and exact (`Decimal` costs, `seq` order). `recorder.py` already defines an `EventSink` seam, so storage plugs in as one more sink.

GDPR also applies. Events can hold personal data: director names from filings, and visitors' task text. Each run's data needs a retention period and a way to erase it (see `docs/governance/gdpr.md` and C11).

## Options considered

**How code talks to Postgres**
- **psycopg 3 + raw SQL + numbered `.sql` migrations.** This is what `multimodal-doc-rag` uses (its ADR 0010).
  - Pros: no hidden queries; one pattern across the portfolio; easy to explain line by line.
  - Cons: we write the mapping and the migration runner ourselves.
- **SQLAlchemy Core + Alembic.**
  - Pros: typed query building; autogenerated migrations; widely used in industry.
  - Cons: a second pattern next to doc-rag; more to learn and defend.
- **An ORM (SQLAlchemy ORM / SQLModel).**
  - Pros: least code for CRUD.
  - Cons: hides the SQL. Weak fit for an append-only log that is mostly inserts and ordered reads.

**How events are stored**
- **One `events` table with typed columns plus a `JSONB` payload, append-only.** The app's database role gets `INSERT` and `SELECT` only.
  - Pros: the database itself enforces append-only; simple ordered reads.
  - Cons: erasure needs its own path (a separate deletable table, or crypto-shredding: C11).
- **A mutable `runs` row plus an `events` table.**
  - Pros: quick status lookups.
  - Cons: two sources of truth unless `runs` is rebuilt from events (C6).

**How a running agent feeds the SSE stream**
- **An in-process `asyncio.Queue` per run.**
  - Pros: simplest; no extra infrastructure.
  - Cons: only works with one server process.
- **Postgres `LISTEN/NOTIFY`.**
  - Pros: works across processes; reuses the database.
  - Cons: payload size limits; more moving parts.
- **Polling by `seq`.**
  - Pros: trivial; can always resume from the last `seq`.
  - Cons: latency and wasted queries.

## Decision
- **Database access: psycopg 3 + raw SQL + numbered `.sql` migrations.** Chosen by the owner on 2026-11-26.
- **Event table shape and SSE feed: still open.** Claude recommends one append-only `events` table, with personal data kept out of chained fields, and an in-process queue for SSE with polling by `seq` for reconnects. To be settled when Phase 6 starts.
